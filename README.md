# Exeris Tooling

Build-time tooling for the Exeris platform: annotation processor, code generators,
and end-to-end conformance tests.

This repository contains the **compile-time pipeline** that turns annotated
Entity-First Java sources (`@ExerisDomain`, `@Action`, `@Field`, …) into clean
kernel-target code: handlers, services, repositories, OpenAPI specs, Flyway
migrations, sagas, and corresponding Angular/TypeScript frontend artifacts.

## Requirements

- **Maven on JDK 25 LTS or newer.** The reactor compiles at `--release 25` and builds
  class v69 artifacts, including `exeris-codegen-maven-plugin`, whose classes load into
  Maven's own JVM — so an older JDK dies at plugin load with an opaque classworlds
  `UnsupportedClassVersionError` realm dump. A `maven-enforcer` rule fails with one
  clear line instead. No `--enable-preview` anywhere, and none imposed on you.
- Maven 3.9+ (enforced alongside the JDK rule).
- Node 18+ to build `exeris-codegen-ts`; the **generated** Angular v22 app targets
  Node 22+.
- `eu.exeris:exeris-kernel-*:0.12.0` and `eu.exeris:exeris-sdk-*:0.12.0`, both final
  releases on Maven Central. Every dependency resolves from Central with no settings
  file, and nothing is built from source first. A local repository that holds a kernel
  `0.12.0` fetched from GitHub Packages, or an SDK `0.12.0` installed from source, before
  the release keeps serving it, because Maven never re-fetches a release; delete
  `~/.m2/repository/eu/exeris/exeris-kernel*` and
  `~/.m2/repository/eu/exeris/exeris-sdk*` once. The POMs name no repository of their
  own, because a published POM would hand that registry to every consumer. Take the
  **`eu.exeris`** kernel coordinates, not `eu.exeris.preview` — the preview line is
  JDK 28 EA with `--enable-preview`, and nothing generated here differs between them.

## Pipeline

```
@ExerisDomain Order.java
        ↓
[ exeris-processor ]               ← reads javax.lang.model at build time
        ↓
exeris-metadata/Order.json         ← canonical DomainMetadata (records defined in
                                     exeris-sdk-source-model)
        ↓
[ exeris-codegen-core ]            ← MetadataLoader + GeneratorRegistry
   ├── exeris-codegen-java         ← kernel-target Java emission
   └── exeris-codegen-ts           ← Angular components, services, stores (npm package, separate build)
        ↓
src/main/generated/java/...        ← committed to repo, regenerated on demand
src/main/generated/typescript/...  ← Studio-friendly clean output
```

## Modules

| Module | Stack | Purpose |
|---|---|---|
| [`exeris-diagnostics`](exeris-diagnostics) | Java 25 | The stable diagnostic identifiers (`EXT-PROC`, `EXT-PLUG`, `EXT-GEN`) every tooling module prints; no dependencies ([reference](docs/diagnostics.md), ADR-095). |
| [`exeris-processor`](exeris-processor) | Java 25 | Annotation processor — extracts `DomainMetadata` from annotated sources at compile time. Self-registered via `@AutoService`. |
| [`exeris-codegen-core`](exeris-codegen-core) | Java 25 | Shared infrastructure: `MetadataLoader`, `GeneratorRegistry`, `KernelArtifactGenerator` interface. |
| [`exeris-codegen-java`](exeris-codegen-java) | Java 25 | Java code generators — kernel-target only (handlers, services, repositories, sagas, events, OpenAPI). |
| [`exeris-codegen-ts`](exeris-codegen-ts) | Node 18+ / TypeScript | Angular generators — component, service, store, guard, form, list, detail, app structure, sagas. |
| [`exeris-e2e-tests`](exeris-e2e-tests) | JUnit 5 | Codegen output verification. Heavyweight runtime integration tests (Postgres, RestAssured) live in downstream platform repos. |
| `exeris-tooling-bom` | — | Bill of materials for this reactor's own build. Not for applications. |
| `exeris-tooling-parent` | — | Common Maven build configuration for this reactor. |
| [`exeris-app-bom`](exeris-app-bom) | — | The tested tooling + kernel + SDK versions, for an application ([Quick start](#quick-start-an-application-on-the-starter)). |
| [`exeris-app-parent`](exeris-app-parent) | — | Parent POM for an application: processor, bound codegen goals, generated resources. |
| [`exeris-app-starter`](exeris-app-starter) | — | The dependency set generated code compiles and runs against (type `pom`). |
| [`exeris-app-starter-it`](exeris-app-starter-it) | Maven Invoker | Builds an application on the parent and the starter with the real plugin. Not published. |

## Targets

**Single target: Exeris kernel.** Spring/Quarkus/Micronaut/Vanilla generators were
removed in this split — the platform commits to a kernel-native runtime story,
with `exeris-spring-runtime` available as a host-Spring-on-kernel migration
bridge for legacy applications (in a separate repo, not generated by this
tooling).

## Quick start: an application on the starter

Tooling generates an application's sources, migrations and OpenAPI, and no build file. Three
published POMs carry the build instead ([ADR-091](docs/adr/ADR-091-opt-in-application-starter.md)),
all versioned with tooling, from 0.9.0:

- **`exeris-app-bom`** names the tooling, kernel and SDK versions this tooling release was built and
  tested against, the kernel's Jackson 3 line, and the starter itself.
- **`exeris-app-parent`** runs the annotation processor, binds `exeris:generate` (`generate-sources`)
  and `exeris:verify-capabilities` + `exeris:verify-runtime` (`process-classes`), compiles at
  `--release 25` on JDK 25+ and Maven 3.9+, and puts the generated migrations (`db/migration`) and
  OpenAPI document (`openapi`) on the classpath.
- **`exeris-app-starter`** (type `pom`) is the dependency set the generated code compiles and runs
  against: the SDK annotations, kernel SPI and Core, the community driver at runtime, the
  composition runtime and Jackson 3.

**The JDBC driver and the logging backend are the application's choice.** The starter declares
neither. Generated code logs through `System.Logger`; to route it, put a `System.LoggerFinder`
provider on the classpath. To run on a driver other than the community one, exclude
`eu.exeris:exeris-kernel-community` from the starter and declare yours; `exeris:verify-runtime`
checks for registered providers, not for a particular artefact.

### Route 1: the parent

```xml
<parent>
    <groupId>eu.exeris.tooling</groupId>
    <artifactId>exeris-app-parent</artifactId>
    <version>0.9.0</version>
    <relativePath/>
</parent>

<groupId>com.example</groupId>
<artifactId>orders</artifactId>
<version>1.0.0</version>
<description>Your application's description.</description>

<!-- The parent carries Exeris's own publication metadata, and anything you do not declare is
     inherited. State yours, or blank it as here. -->
<url/>
<licenses>
    <license/>
</licenses>
<developers>
    <developer/>
</developers>
<scm>
    <connection/>
    <developerConnection/>
    <tag/>
    <url/>
</scm>

<dependencies>
    <dependency>
        <groupId>eu.exeris.tooling</groupId>
        <artifactId>exeris-app-starter</artifactId>
        <type>pom</type>
    </dependency>
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <version>42.7.13</version>
        <scope>runtime</scope>
    </dependency>
</dependencies>
```

The parent manages the starter's version, so the tooling version appears once, on the parent. The
parent is a published Exeris POM and carries Exeris's `url`, `licenses`, `developers`, `scm` and
`description`; the empty elements above keep them out of your effective POM. A `<resources>` section
in your POM replaces the parent's, so keep its `src/main/generated/java` entry (below) if you
declare one.

### Route 2: an application that already has a parent

Import the BOM and copy the build block. An imported BOM brings `dependencyManagement` only: Maven
imports no properties, `pluginManagement` or goal bindings from it, which is why the block is copied
and why the tooling version is a property of your own.

```xml
<properties>
    <exeris.tooling.version>0.9.0</exeris.tooling.version>
    <maven.compiler.release>25</maven.compiler.release>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>eu.exeris.tooling</groupId>
            <artifactId>exeris-app-bom</artifactId>
            <version>${exeris.tooling.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>eu.exeris.tooling</groupId>
        <artifactId>exeris-app-starter</artifactId>
        <type>pom</type>
    </dependency>
    <!-- your JDBC driver, at runtime scope -->
</dependencies>

<build>
    <resources>
        <resource>
            <directory>${project.basedir}/src/main/resources</directory>
        </resource>
        <resource>
            <directory>${project.basedir}/src/main/generated/java</directory>
            <includes>
                <include>db/migration/**</include>
                <include>openapi/**</include>
            </includes>
        </resource>
    </resources>
    <plugins>
        <!-- BEGIN exeris build block: identical to exeris-app-parent's -->
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <annotationProcessorPaths>
                    <path>
                        <groupId>eu.exeris.tooling</groupId>
                        <artifactId>exeris-processor</artifactId>
                        <version>${exeris.tooling.version}</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
        <plugin>
            <groupId>eu.exeris.tooling</groupId>
            <artifactId>exeris-codegen-maven-plugin</artifactId>
            <version>${exeris.tooling.version}</version>
            <executions>
                <execution>
                    <id>exeris-generate</id>
                    <phase>generate-sources</phase>
                    <goals>
                        <goal>generate</goal>
                    </goals>
                </execution>
                <execution>
                    <id>exeris-verify</id>
                    <phase>process-classes</phase>
                    <goals>
                        <goal>verify-capabilities</goal>
                        <goal>verify-runtime</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
        <!-- END exeris build block -->
    </plugins>
</build>
```

The block is the one `exeris-app-parent` binds, kept identical to it. The invoker fixture
(`exeris-app-starter-it`) builds route 1 only, so this copy is checked by review, not by a build.

### The first build takes two passes

The processor writes `target/classes/exeris-metadata/*.json` during `compile`, which runs after
`exeris:generate` at `generate-sources`. On a tree with no metadata yet, seed it first:

```bash
mvn compile -Dexeris.codegen.skip=true   # pass 1: compile your entities; the processor writes the metadata
mvn verify                               # pass 2: generate, compile, verify-capabilities, verify-runtime, test
```

Do not `clean` between the passes: it deletes the metadata pass 1 wrote. Once the generated tree under
`src/main/generated/java` is committed, every build is a single pass.

### Commit the generated tree once your own code depends on it

Hand-written code that extends or imports a generated type, for example a class that `extends` a
generated `*SagaFlow`, compiles only while that type exists. So once such code is in the tree,
deleting `src/main/generated` and rebuilding is not a safe loop: the first pass compiles your
sources before `exeris:generate` has anything to generate from, and fails on the missing types.
Keep `src/main/generated/java` committed, and regenerate over it rather than from an empty tree.
To own the code outright, run `mvn exeris:detach`. It moves the generated sources into
`src/main/java` and leaves any file that already exists there untouched. Then remove the
`exeris:generate` execution from your build.

### Generated tests

Set `<exeris.tests>true</exeris.tests>` to emit tests for the generated code under
`src/test/generated/java` ([ADR-058](docs/adr/ADR-058-generated-test-emission-channel.md)). They need JUnit 5 and AssertJ in your `test` scope
and nothing else; the starter carries neither.

## Build

> **Note:** `exeris-codegen-ts` is **not** part of the Maven reactor. The Java
> and TypeScript generators are built independently — `mvn install` builds only
> the Java side. Build the TS generator separately as shown below.

```bash
mvn clean install                                  # build + test Java modules (no TS)
cd exeris-codegen-ts && npm install && npm test    # frontend generator (separate build)
```
