## Question

When a user app re-enables on-demand regeneration via `exeris:reattach`, how does the pipeline detect that someone edited a **generated** file in place (instead of using the intended "Custom" extension pattern of separate consumer classes), and avoid silently overwriting that work — and what provenance mechanism makes that detection trustworthy across self-hosted, managed-infra, and bring-your-own-repo deployment shapes?

## Context

`exeris:detach` (0.3.0, PR #70) promotes generated code from L1 (`src/main/generated/`, pipeline-owned) to L2 (`src/main/java/`, user-owned), and is intentionally one-way today. `exeris:reattach` is the planned inverse (ROADMAP.md:39) that re-enables regeneration. Its long-standing blocker — re-deriving `DomainMetadata` from owned `.java` without `javac` — is now **cleared**: `SourceModelReader` (`exeris-sdk-source-model-io`) round-trips all facets and `unmodeledFacets()` returns empty (Slices A–D complete).

That unblocks the *mechanical* half of reattach (resume regen). It does **not** answer the *safety* half. The whole point of the "Custom services" contract is that business logic lives in **separate** hand-authored classes that consume the generated `*Service`/`*Repository`; generated files carry `DO NOT EDIT` and stay pipeline-owned. But nothing enforces that. A non-expert (or a rushed expert) can paste important logic directly into a generated file. If reattach then regenerates over it, that work is lost — silently. This is the failure mode the RFC must design against.

The question broadens on examination. "Where does the trust anchor live?" turns out to depend on **two independent axes** — where the source of truth lives (user's git repo vs. an Exeris-hosted control plane) and where the app runs (user infra vs. Exeris-hosted infra) — yielding three real personas with materially different requirements. No Exeris-hosted infra exists yet, so v1 only needs the self-hosted persona; but the interfaces must not be designed so narrowly that the other two force a rewrite.

## Investigation

### Prior art

- **Dependabot / Renovate** — a bot proposes machine-generated changes via PR; a human merges. The bot never force-pushes over human edits. This is the canonical multi-writer pattern and maps directly onto the "hosted infra regenerates while the user also edits" persona (P3 below).
- **Vercel / Netlify git integration** — "bring your own repo, the platform hosts and deploys from it." The repo is the source of truth; the platform reacts to pushes via webhooks. This is the shape P3 takes.
- **`go generate`, protoc, OpenAPI generators** — emit a `DO NOT EDIT` banner and assume regeneration clobbers. None solve in-file-edit safety; they push extension into separate files. This is exactly the "Custom services" contract — and exactly the contract that has no enforcement today.
- **3-way merge (git)** — given a common ancestor (the originally-generated bytes), a user-edited version, and a freshly-regenerated version, git merges deterministically and surfaces true conflicts. Requires retaining the ancestor.

### Constraints

Bound by `exeris-tooling/CLAUDE.md` hard constraints:
- **#3 Determinism** — same `DomainMetadata` → byte-identical output. A reattach baseline built by *regenerating* depends on this holding across the *same* tooling version; it does **not** hold across versions (see "Data gathered").
- **#4 Metadata is the only contract** — reattach's regeneration must go through `DomainMetadata` re-derived by `SourceModelReader`, not by re-reading `Element`/`TypeMirror`.
- **#6 Detachment is load-bearing** — reattach is the documented inverse; it must not assume "always regenerate."

### Data gathered

Three independent sources of a generated-vs-on-disk diff, only one of which should be flagged:

1. **User edited a generated file** — the target signal.
2. **Reader infidelity** — `unmodeledFacets() == ∅` certifies *annotation-level* parity and `@Field`/`@Validation` attribute-completeness (Slice D), but attribute-completeness of `@Relationship`/`@Action`/`@UI`/`@ExerisDomain` is "verified per-slice rather than by this method" (`SourceModelReader.java:184-189`). A dropped attribute → regenerated ≠ original with **zero** user edits → false positive. The reader is also simple-name-matched (no import resolution) and not thread-safe.
3. **Generator-version drift** — detached on tooling vX, reattached on vY. Generator output legitimately changes between trains (the 0.4.0 emission-strategy work itself is a series of such changes; PR #75 happens to be byte-identical, but that is the exception, not the rule). → false positive.

A naïve regenerate-and-compare **conflates all three**. False positives erode trust ("it always complains"); a false negative (reader coincidentally reproduces the edited form) silently loses data — the nightmare case.

Current codebase has **no provenance mechanism**: `GeneratedFile` is `(packageName, className, content, artifactType, extension)` with no hash/version field; `DetachService` *moves* bytes and writes no manifest. The only "this is generated" signal is the `DO NOT EDIT` Javadoc line plus the L1 location — and detach destroys the location signal.

### The persona matrix (the core finding)

|  | Deploy: **user infra** | Deploy: **Exeris-hosted infra** |
|---|---|---|
| **Truth: user's git repo** | **P1** — self-hosted detach. Manifest in-tree, single writer. *(v1 target)* | **P3** — BYO-repo + hosted infra. Two concurrent writers (user edits + pipeline regen). |
| **Truth: hosted control plane** | edge case (negligible) | **P2** — fully managed, non-technical user. Full snapshot held server-side. |

The personas are **combinations of three orthogonal concerns**, not three separate engines:

1. **`ProvenanceBaseline`** — *what* the baseline is: a content **hash** (cheap, detection-only) or a full **snapshot** of the originally-emitted bytes (enables true 3-way merge).
2. **`ManifestStore`** — *where* it lives: in-tree (committed to the user's repo) or in a hosted control plane (keyed by instance id; the user never touches git).
3. **`WriteBackStrategy`** — *how* regen is applied when ≥1 writer exists: **apply-or-refuse** (single writer; `--force` to override) or **propose-via-PR** (multi-writer; git is the merge engine, Dependabot model — never clobber).

Precision improves up a fidelity ladder that falls out naturally:
- **Tier 0 — no manifest** (legacy detach): fall back to reader-regenerate-and-compare; advisory only, all three caveats apply.
- **Tier 1 — hash manifest** (P1, in-repo): *exact edit detection*; to *show/merge* the edit you still regenerate (reader-bound).
- **Tier 2 — full snapshot** (P2/P3, hosted storage available): true 3-way merge, **zero** reader dependence.

Punchline: the persona least able to resolve a merge conflict (P2, non-technical) lands in the **highest** tier, because hosted infra retains the original. The precision problem is worst exactly where the user is most technical (P1) — which is acceptable, because that user can read a diff.

### Spike outcomes

None built. This RFC precedes any reattach code. The `SourceModelReader` round-trip (the precondition) is independently verified shipped.

## Options Considered

### Option A: Regenerate-and-compare only (no manifest)

Reattach re-derives metadata via `SourceModelReader`, regenerates each artifact, diffs against the on-disk file, flags differences as "user edits."

**Pros:**
- No new artifact; no change to `detach`.
- Works retroactively on already-detached apps.

**Cons:**
- Conflates all three diff sources (§Data gathered). False positives kill trust; false negatives lose data silently.
- Trust is bounded by reader attribute-fidelity, which is explicitly *not* guaranteed for `@Relationship`/`@Action`/`@UI`.

**Cost:** Low to build, high in eroded trust and data-loss risk.

### Option B: Hash manifest at detach (detection anchor), reader only for explanation

`detach` writes a manifest: per promoted file, SHA-256 of the exact emitted bytes + `artifactType` + FQN; header carries tooling version, generator versions, and a digest of the source `DomainMetadata`. Reattach compares on-disk bytes to the recorded hash — mismatch = user edit, **exactly**, independent of reader fidelity and generator version. The reader/regeneration is used only to *explain* (semantic diff) and to drive resume-regen, never as the trust anchor.

**Pros:**
- Cleanly separates all three diff sources; detection is exact.
- No control-plane needed; manifest is a small committed file.
- Version fields let reattach distinguish "you're on newer tooling" (expected) from a real edit.

**Cons:**
- Only **detects**; to render/merge the edit it still regenerates (reader-bound) — acceptable because that path is explanatory, not the gate.
- Requires `detach` to start writing the manifest **before** reattach ships, or early-detached apps have no baseline.

**Cost:** Small: a provenance record + manifest write in `DetachService`, a comparator in reattach.

### Option C: Full provenance + pluggable store + write-back strategies (the matrix)

Option B's mechanism, generalized along the three orthogonal interfaces so all three personas are combinations, not forks: `ProvenanceBaseline` (hash | snapshot), `ManifestStore` (in-tree | control-plane), `WriteBackStrategy` (apply-or-refuse | propose-PR). **v1 implements only P1** (hash baseline, in-tree store, apply-or-refuse); P2 (snapshot + control-plane) and P3 (snapshot + propose-PR + git webhooks) are designed-for, deferred.

**Pros:**
- One mechanism, three small strategy enums — no engine explosion.
- The non-technical persona (P2) gets the highest-fidelity machinery for free once infra exists.
- P3 (BYO-repo + hosted infra) drops onto git's native 3-way merge via the Dependabot model — exactly what a technical customer-founder expects.

**Cons:**
- More interface surface than v1 strictly needs; risk of speculative generality if the deferred tiers never ship.

**Cost:** v1 cost ≈ Option B. The extra cost is *interface design discipline* (two enums and a store seam), paid once, up front.

### Option C (do nothing)

Ship reattach as a blind L2→L1 round-trip with no edit detection.

**Cons:** Directly causes the silent-data-loss failure mode this RFC exists to prevent. Unacceptable.

## Recommendation

**Adopt Option C: the content-addressed provenance mechanism of Option B, generalized into three orthogonal interfaces (`ProvenanceBaseline` / `ManifestStore` / `WriteBackStrategy`), with v1 implementing only persona P1 (self-hosted, in-tree hash manifest, apply-or-refuse).**

Detection trust must be anchored on what was *emitted*, not on what can be *re-derived*. A content hash captured at `detach` time separates the three diff sources exactly and cheaply; the reader (whose attribute-fidelity is explicitly not guaranteed for several facets, `SourceModelReader.java:184-189`) is demoted to an *explainer*, where its imperfections are tolerable. This is Option B, and Option B is the right core.

Option C generalizes B because the persona analysis showed the three deployment shapes are **combinations of three small choices**, not three engines — so the generality is nearly free at the interface layer, while a narrow P1-only design would force a rewrite the moment hosted infra (P2) or BYO-repo integration (P3) lands. No hosted infra exists yet, so building P2/P3 now would be speculative; but *designing the seams* now is the cheap insurance. The fidelity ladder (hash → snapshot) and the write-back split (apply-or-refuse → propose-PR) are written into the RFC so the deferred work has a fixed shape to grow into.

### Why not the alternatives?

- **Option A** — conflates user-edit / reader-infidelity / version-drift; risks silent data loss, the exact thing reattach must prevent.
- **Option B (as the ceiling)** — correct mechanism but P1-only framing; would force interface rework when P2/P3 arrive. C keeps B's v1 cost while fixing the seams.
- **Do nothing** — directly causes the failure mode.

### Risks of the recommendation

- **Speculative generality** — if P2/P3 never ship, two strategy seams are unused. Mitigation: the seams are enums + one interface, not infrastructure; v1 ships exactly one implementation of each.
- **Sequencing trap** — reattach is only trustworthy for apps detached *with* the manifest. `detach` must emit the manifest in a release **preceding** reattach, and reattach must degrade to Tier 0 (advisory) for manifest-less apps and say so loudly.
- **Manifest drift** — a committed in-tree manifest can itself be hand-edited or go stale vs. the files. Mitigation: treat a missing/garbled manifest as Tier 0, never as "no edits."
