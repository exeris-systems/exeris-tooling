# ADR-059 — Data-scope expression: `DataScope { GLOBAL, TENANT, UNIVERSE }` supersedes `tenantScoped` (link stub)

**Authoritative copy:** [`exeris-sdk/docs/adr/ADR-059-data-scope-expression.md`](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/adr/ADR-059-data-scope-expression.md)

ADR-059 is a **cross-repo** decision owned by `exeris-sdk`, shipped in SDK **0.10.0**. `@ExerisDomain.dataScope` — a mutually-exclusive `DataScope { GLOBAL, TENANT, UNIVERSE }` discriminator — becomes the canonical expression of an entity's data-scope tier, and `@ExerisDomain.tenantScoped` is `@Deprecated(since = "0.10.0", forRemoval = true)` with the fallback `true → TENANT` / `false → GLOBAL`. Driven by [RFC-2026-06-24](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/rfc/RFC-2026-06-24-universe-data-scope-expression.md).

> Cross-repo link-stub: the authoritative copy lives in the repo named above; the URLs resolve to their canonical GitHub locations. Convention catalogued in `exeris-docs/adr-index.md` → *Cross-repo stubs*.

## Why this stub exists — `exeris-tooling` carries the transcription obligation

ADR-059 obligation 5 is addressed to this repo by name, and `UNIVERSE` ships **reserved** precisely because that obligation is unbuilt: the SDK can now express the tier, but nothing maps it onto the kernel carrier until tooling transcribes it. The reserved note in the annotation javadoc stands or falls on this slice.

Obligation 5 has four parts:

- **extract `dataScope`** from `@ExerisDomain` into `DomainMetadata`;
- **read `tenantScoped` as a fallback with a build warning** while `dataScope` is `UNSPECIFIED` — the standard deprecation window, not a silent equivalence;
- **reject a declared tier that contradicts a declared `tenantScoped`** (e.g. `dataScope = GLOBAL, tenantScoped = true`) rather than resolving it by precedence rules nobody can see;
- **map `UNIVERSE` onto presence of the kernel `sharedScopeKey` carrier** (ADR-012 §4b, kernel 0.11 line) and `TENANT` / `GLOBAL` onto its absence.

## The call sites — and why this is not a pure extraction change

Every generator that consumes the tier today reads the raw boolean:

| Site | What the boolean decides |
|---|---|
| `exeris-processor/…/ExerisDomainProcessor.java:905` | extraction — the only write site |
| `exeris-codegen-java/…/kernel/KernelFlywayGenerator.java:82` | whether an RLS policy is emitted at all |
| `exeris-codegen-java/…/kernel/KernelFlywayGenerator.java:105` | the `migrationVersion` tier discriminator (`V1xxxxxx` vs `V2xxxxxx`) |
| `exeris-codegen-java/…/kernel/KernelFlywayGenerator.java:118` | the `tenant_id UUID NOT NULL REFERENCES tenants(id)` column |
| `exeris-codegen-java/…/kernel/KernelFlywayGenerator.java:217` | the tenant-column index — `buildIndexes` emits `idx_<table>_tenant` and seeds `indexedColumns` with the tenant column, so this read also decides whether a *later* filterable/searchable field on that same column gets a second, duplicate index |
| `exeris-codegen-java/…/kernel/KernelRepositoryGenerator.java:341, 367` | the tenant column in the system-column set and the column layout |
| `exeris-codegen-java/…/dsl/DomainMetadataGenerator.java:67` | the `multiTenant` flag in the emitted DSL JSON |
| `exeris-codegen-ts/src/models/domain-model.ts:295` | the zod schema mirror of the AST field |
| `exeris-codegen-ts/src/generators/angular/store-gen.ts:47` | nothing — destructured and never read. A dead binding, but it is the shape a future reader would copy, so it counts as a call site |

Because these read `metadata.tenantScoped()` and not `DomainMetadata.effectiveDataScope()`, an author who writes `dataScope = TENANT` **without** also writing `tenantScoped = true` would get a table with no RLS policy, no tenant column, no tenant index and a tier-1 migration version — a silent loss of tenancy, not a build error. Migrating the read sites to `effectiveDataScope()` therefore belongs to the same slice as the extraction; shipping the extraction alone would make the new attribute actively dangerous rather than merely inert.

The table is meant to be the **exhaustive** migration checklist, so treat it as one: re-derive it with `grep -rn 'tenantScoped'` at the start of the slice rather than trusting these line numbers, which drift with every unrelated edit above them. It is worth being explicit that a partial migration is the dangerous outcome — a generator half-moved to `effectiveDataScope()` emits a table whose RLS policy and tenant column disagree with its index set, which is worse than either extreme.

The fallback is what keeps existing corpora byte-stable: for a source that declares only `tenantScoped`, `effectiveDataScope()` returns exactly what the boolean always meant, so emitted SQL, column layouts and Flyway versions do not move. Only a newly declared tier changes output — and a `GLOBAL → TENANT` change moves the entity across the `migrationVersion` tier discriminator, which Flyway sees as a **new migration** rather than an edit to the existing one. That has always been true of a `tenantScoped` flip; it is worth restating because a one-word enum change makes it easier to do without noticing.

## Also in scope: the schema bump

`SchemaVersion.CURRENT` moves `"0.9.0"` → `"0.10.0"`. Per [ADR-042](ADR-042.link.md) the processor stamps `schemaVersion` into each `exeris-metadata/<entity>.json`, and a reader on a different version refuses the baseline (`SCHEMA_VERSION_SKEW` → `NO_BASELINE`) rather than compare across shapes. So bumping `exeris.sdk.version` in `exeris-tooling-bom/pom.xml` needs a one-time codegen re-run for downstream baselines to re-stamp — the same lockstep [ADR-054](ADR-054.link.md) required at `"0.9.0"`.

## When to consult ADR-059 from tooling

- Adding or changing any read of `metadata.tenantScoped()` — after this slice the canonical read is `effectiveDataScope()`, and a raw read of the deprecated boolean is a bug that produces the wrong DDL rather than a compile error.
- Deciding what `UNIVERSE` emits — the SDK deliberately encodes author intent only and never the `StorageContext` carrier. The mapping onto `sharedScopeKey` is tooling's, and the row-visibility semantics are the kernel's; do not invent a third model here.
- Extending the zod mirror in `exeris-codegen-ts` — the TS schema tracks the AST record, so a new AST component needs a matching field there or the TS emitter silently drops it.
- Removing `tenantScoped` — not before SDK **1.0.0**. The deprecation window is the whole 0.10.x–0.9x line; the processor fallback is what makes that window real.

## Engineering status

ADR-059 is **ACCEPTED** (2026-07-31); the SDK side merged 2026-08-02 (`exeris-sdk` **#89**).

**Slice A — landed.** Three of obligation 5's four parts ship: `ExerisDomainProcessor` extracts `dataScope`, warns when a build still resolves its tier through the deprecated boolean, and rejects a declared tier that contradicts a declared `tenantScoped` (the fallback mapping is total, so the check is exact — no boolean value agrees with `UNIVERSE`). Every raw `metadata.tenantScoped()` read in the emitters now goes through `DataScopeSupport.isTenantPartitioned`, the one place that asks what a tier means for output. `exeris-codegen-ts` mirrors the field and gains `effectiveDataScope`, the TS twin of the Java accessor; the store generator's dead `tenantScoped` destructure is dropped rather than migrated, since re-deriving the table with `grep` — as this section instructs — is how it surfaced in the first place. The SNAPSHOT window this slice opened is **closed**: `exeris.sdk.version` is the released `0.10.0` and CI checks out the `v0.10.0` tag again, as of U0.

**Slice B — open, and gated on the kernel 0.12 pin (B0).** The fourth part maps `UNIVERSE` onto the kernel's shared-scope carrier. `StorageContext.sharedScopeKey()` is on the pinned `v0.11.0` line, and reading only that is how this repo came to say in five places — including a `javac` message — that the gate was gone. **It is not:** an emitted RLS policy does not read an accessor, it names a PostgreSQL session variable, and at `v0.11.0` `exeris.tenant_id` is named in SPI (4 files), Core and the TCK while `exeris.shared_scope` is named in `exeris-kernel-community` and in no SPI, Core or TCK file. The persistence driver is swappable Community/Enterprise, so a migration the consumer commits may not depend on one driver's internal literal — which is exactly why the tenant policy already emitted is sound and this one is not yet emittable. Kernel 0.12 promotes both names to constants on `ConnectionInterceptor` (`SESSION_KEY_TENANT_ID`, `SESSION_KEY_SHARED_SCOPE`); that is the gate. A second half is missing independently of the pin: the policy also needs a shared-scope **column**, and no SDK carrier names one (`SystemFieldsMetadata` declares ten components and none is it), so slice B owes the SDK an ask as well as the kernel a pin. Until slice B is built, `UNIVERSE` **fails closed to the TENANT shape**: owner column, owner index and an owner-pinned RLS policy, i.e. UNIVERSE minus the cross-tenant read-widen, with a processor warning saying exactly that. The alternative — treating an untranscribable tier as `GLOBAL` — would drop the owner column and the policy and publish rows the author scoped to an owner, so the predicate is deliberately "not `GLOBAL`" rather than "is `TENANT`". When both halves land, `UNIVERSE` gains its own case in `DataScopeSupport` rather than at seven call sites.

The SDK's `exeris-sdk-source-model-io` reader parity is the other half of this lockstep (ADR-042 discipline — the reader reads what the processor writes). It becomes correct to take the moment slice A lands, not before.
