# ADR-072 — `@Blob` and `@Schedule`: a design-time surface for the kernel 0.11 preview SPI (link stub)

**Authoritative copy:** [`exeris-sdk/docs/adr/ADR-072-kernel-preview-spi-reserved-surface.md`](https://github.com/exeris-systems/exeris-sdk/blob/main/docs/adr/ADR-072-kernel-preview-spi-reserved-surface.md)

ADR-072 is a **cross-repo** decision owned by `exeris-sdk`, shipped in SDK **0.11.0**. Kernel v0.11
added two SPI packages — `eu.exeris.kernel.spi.storage.blob` (kernel ADR-056) and
`eu.exeris.kernel.spi.scheduling` (kernel ADR-057) — each naming an Entity-First gap the SDK could
not express. `@Blob` (field-level, AST carrier `FieldMetadata.blob`) and `@Schedule` (method-level,
alongside `@Action`; AST carrier `ActionMetadata.schedule`) close the design-time half. Both ship
**reserved** and **outside the 1.0.0 freeze**.

> their canonical GitHub locations. Convention catalogued in `exeris-docs/adr-index.md` →
> *Cross-repo stubs*.

## Why this stub exists — `exeris-tooling` is the named consumer

"Reserved" is not a property of the annotation; it is a statement about this repo. ADR-072 obligation 1
holds both surfaces reserved *until the transcription exists here*, and kernel ADR-056 asked for the
sequencing by name ("`exeris-tooling` gains something to generate against"). The promotion condition
is two-part and neither half is ours alone:

1. the kernel promotes `…spi.storage.blob` / `…spi.scheduling` out of tier `preview` in its
   `docs/stability-matrix.md`; **and**
2. the transcription exists in this repo.

## Measured state in this tree (2026-08-27)

- The pin is on the released coordinate: `exeris.sdk.version` is `0.11.0` (U3, PR #175), so both
  annotations and both AST carriers are on the compile classpath here today.
- `ExerisDomainProcessor` references neither annotation — `grep -rn 'Blob\|Schedule'` over
  `exeris-processor/src/main` finds no `eu.exeris.sdk.annotation` FQN for either.
- No generator, Java or TS, reads `FieldMetadata.blob` or `ActionMetadata.schedule`.
- **Neither owes an `INERT_ATTRIBUTES` / `INERT_ANNOTATIONS` entry yet.** The registries describe
  attributes the processor *extracts* and no generator consumes; these are pre-extraction, not
  post-extraction-unconsumed, so `-Aexeris.strict` is correct to stay silent. The entries become owed
  in the same change that starts extracting — and per D5, each needs its `warnInertAttributes` call
  site or it is a dead entry.
- `-io` reader parity is **not** owed either, on the ADR-042 discipline: the reader reads what the
  processor writes, and the processor writes neither. Reading ahead would manufacture drift.

## Two build-time rejections, handed to this repo rather than left to be rediscovered

ADR-072's Open Questions name both. Re-verified against kernel **v0.11.0** — the tag this repo pins —
rather than transcribed:

Cited by **symbol and section, never by line number** — the `GLOBAL` constant alone sits at
`ImmutableStorageContext.java:59` on `v0.11.0` and `:55` on the kernel's active `development/0.12.0`,
so a line citation here would have been stale before this file merged.

| Declaration | Why the platform refuses it | Evidence at `v0.11.0` |
|---|---|---|
| `@Blob` on a `dataScope = GLOBAL` entity | Every `BlobStore` operation resolves its `BlobRef` against `StorageContext.isolationKey()`, and an absent key is a **terminal deny**, never an unscoped fallback. `DataScope.GLOBAL` is exactly the tier that leaves it empty. | `BlobStore` class javadoc, terminal-deny clause (ADR-056 §5), plus every method's `@throws BlobStorageException if the ambient context carries no isolation key`; the `ImmutableStorageContext.GLOBAL` constant, built with `Optional.empty()` as its isolation key |
| `@Schedule` on an action, with no answer to *whose identity it runs as* | `JobScheduler.submit(...)` captures the ambient `PrincipalContext` and `StorageContext` and rebinds them at dispatch; a job submitted with neither bound **fails closed** rather than running under a default identity. A declared schedule has no submission event, so there is nothing to capture. | `JobScheduler` §*Identity crosses the boundary by capture* (ADR-057 §5) |

Two sentences from those same javadocs sharpen both rows past "the key happens to be absent":

- `GLOBAL` is not a tier that *lacks* an isolation key incidentally. The `ImmutableStorageContext`
  record javadoc derives a structural property from the absence — `sharedScopeKey` "MUST NOT be
  present without an `isolationKey`, because the shared-scope write predicate pins
  `owner = isolationKey` and has nothing to pin to otherwise. This is what makes `GLOBAL` (system
  scope, no isolation key) structurally incapable of carrying a shared scope."
- `JobScheduler`: "The capture is a **snapshot** — a job firing an hour later carries the authority
  that scheduled it, which may since have been revoked." So the identity question cannot be deferred
  to runtime "at the first submit": there is no scheduling authority to snapshot in the first place.

### The two refusals are coupled

Not obvious from either row on its own, and it constrains the fix rather than just the diagnosis.
If the identity of a declared job resolves to a *system* principal, that job's `StorageContext` is
`GLOBAL` — which is row 1. A declared `@Schedule` whose action touches a blob would then start and
fail to write: fail-closed and correct, but at runtime, and reported as an isolation failure rather
than a scheduling one.

So whatever supplies identity through the `RuntimeComponents` seam has to be able to **name a
tenant**, not merely "system" — otherwise it closes the scheduling refusal and opens the blob one.
A design-time attribute that can only say "run as system" is a half-answer, and specifically the half
that does not suffice.

The first is a combination to **reject at build time with a diagnostic** — system-scope blob storage
is named out of scope by kernel ADR-056, so it is not an oversight to route around.

The second is **not ours to settle**. The answer is either a kernel-side system/service principal for
declared jobs, or an SDK attribute naming the identity to run as — and the latter puts an
authorization decision in a design-time annotation. Owner: kernel, with this repo as the consumer.
A transcription that emits a `submit(...)` before that is answered produces a job that fails closed
on every fire, which is the inert-output failure mode this repo rejects elsewhere.

## What a transcription slice owes

Not designed here — recorded so the slice starts from the constraints rather than from a blank page:

- **`@Blob`** is additionally gated on the runtime, and not by preview tier: `Application.main()` boots
  subsystems *by name*, and there is **no `CommunityStorageSubsystem`** among the ten bootable ones
  (crypto, events, flow, graph, http, memory, persistence, scheduling, security, transport). A
  generated app has no name to declare, which is why the annotation-coverage inventory in `ROADMAP.md`
  carries `@Blob` as the single kernel-gated exclusion (K6) and targets **50 of 51**. That is the
  *smaller* half of K6 — the wider reading, and the three traps under it (a name without a selection
  key emits an app that fails startup by design, because two Community blob providers share a
  priority; no `KernelProviders` slot exists and `STORAGE_CONTEXT` is the ADR-012 isolation carrier,
  not a store; `CommunityProviderInventory` sweeps nine SPIs and blob storage is not one) are recorded
  under K6 in `ROADMAP.md`.
- **`@Schedule`** has its subsystem — `scheduling` is on that list — so it is gated only on the
  submitter question above.
- **The design-time half of `@Blob` is not blocked by any of that**, and a slice that takes it should
  know two things first.

  **`@Blob` is `@Target(FIELD)`, and `warnInertAnnotations` only inspects type-level mirrors.** It
  takes a `TypeElement`; both call sites pass one. So an `INERT_ANNOTATIONS` entry for `@Blob`
  (`FIELD`) or `@Schedule` (`METHOD`) added today would never fire — the D5 defect exactly, one
  registry up. See **D6** in `ROADMAP.md`.

  The repair is small: `findAnnotation` already takes `Element`, and the per-element traversals
  already exist and already host the twin sweep (`warnInertAttributes("Field", …)` on fields, the
  same for action methods). Widening the parameter plus two call sites adds no new traversal.

  **One placement trap, and it is the D5 bug shifted by one call.** The sweep belongs in the field
  *loop*, not inside `extractFieldMetadata` — that extractor sits behind `findAnnotation(field,
  "…annotation.Field") != null`, and a `@Blob` field with no `@Field` is a real shape, since `@Blob`
  describes a byte carrier rather than a column. The loop's `else` branch already admits such a field
  to the model through `FieldMetadata.simple(...)`, so gating the sweep on `@Field` would skip a
  warning for a field that is nonetheless in the AST. A warning whose reachability depends on where
  it is called from is the defect D5 closed; inheriting somebody else's condition is the same thing.

  **Extraction is available, not free.** It re-arms the ADR-042 lockstep: once the processor writes
  `FieldMetadata.blob`, the SDK `-io` reader owes the matching read, and `exeris-codegen-ts` owes the
  parity mirror (hard constraint 5). One correction to ADR-072 obligation 7 belongs with that — it
  says the `unmodeledFacets()` guard "keys on annotation types, so a source using `@Blob` or
  `@Schedule` will correctly report an unmodeled facet". As shipped at `v0.11.0` it does not:
  `SourceModelReader.UNMODELED_FACET_ANNOTATIONS` is `Set.of()`, and `unmodeledFacets` tests
  membership in it, so neither annotation is flagged. The guard is armed by adding the names, and
  nobody added them.
- Both carriers are trailing and additive, and `SchemaVersion.CURRENT` already moved `0.10.0` →
  `0.11.0` for them (see the 0.8.0 train in [`../MIGRATION-0.x-to-1.0.md`](../MIGRATION-0.x-to-1.0.md)).
  A consumer holding a pre-`0.11.0` baseline reads back as `SCHEMA_VERSION_SKEW` and re-runs codegen
  once; that has already happened and is not owed again by the transcription.
