# ADR-083 — A kernel exception says whose fault it is (link stub)

**Authoritative copy:** `exeris-kernel` repo → `docs/adr/ADR-083-exception-fault-origin.md` (a sibling repository, not a path within this repo, so no in-repo link is possible).

ADR-083 is a per-repo decision owned by `exeris-kernel` (scope `kernel/spi`). It extends the status
split ADR-036 §2 rules for request-body decoding. Every `ExerisKernelException` answers *whose
fault* a failure is through a non-final `faultOrigin()`, returning the new
`eu.exeris.kernel.spi.exceptions.FaultOrigin`: `CALLER` (the request is at fault, and repeating it
unchanged fails the same way) or `SYSTEM` (the runtime, its configuration or its dependencies are
at fault). `SYSTEM` is the default. `FaultOrigin.classify(Throwable)` applies the same default to a
throwable that is not a kernel exception, so a JDK exception is never guessed to be the caller's
from its type. The enum says who is at fault, not what status to answer, and it may gain constants,
so a `switch` over it needs a `default`. `…spi.exceptions` is a `stable` surface since kernel 0.12.

## What exeris-tooling consumes

- **The emitted handler's `parseBody`** (`KernelHandlerGenerator.buildParseBody`). A decode failure
  is answered `400` only when `FaultOrigin.classify(e) == FaultOrigin.CALLER`. In kernel 0.12 that
  is `RequestBodyDecodeException`, which the `HttpRequestBodyDecoder` contract requires for a
  malformed body. Any other failure is wrapped and answered `500` by the emitted
  `respondDecodeFailed`. The test is an equality against `CALLER` rather than an `instanceof`, so a
  kernel exception classified `CALLER` later is answered `400` without regenerating.
- **The emitted handler test** (`KernelHandlerTestGenerator`, `exeris.tests`). It drives that
  mapping with a decoder that throws `RequestBodyDecodeException`, a `SYSTEM` kernel exception and a
  JDK exception.
- **Tooling's own caller-fault refusals** (`<Entity>TenantMismatchException`,
  `<Entity>SharedScopeMismatchException`). These are emitted types, not kernel exceptions, and are
  answered `400` by a typed `catch`. They follow ADR-083's `CALLER` definition, but `classify` does
  not see them.

## When to consult ADR-083 from exeris-tooling

- Any change to how an emitted handler maps a failure to a status code: read the fault origin, do
  not infer it from a JDK exception type.
- Any new emitted `catch` over kernel exceptions: compare with `CALLER`, never `switch` without a
  `default`.
