# ADR-089 — Capability Entitlement Enforcement and Runtime Execution Contract (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-089-capability-entitlement-enforcement-and-runtime-contract.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-089-capability-entitlement-enforcement-and-runtime-contract.md)

ADR-089 is a cross-repo decision owned by `exeris-docs`, binding `exeris-kernel`, this repository
and `exeris-platform`. It separates building from licensing: source-available capabilities always
compile, test and package without a manifest, and only a build stamped for a production target has
to prove its entitlements. The kernel is the runtime enforcement point — Phase 0 of its bootstrap
turns the verified manifest into an immutable `ExecutionContract` with `HARD`, `SOFT` and `AUDIT`
levels.

## What it asks of exeris-tooling

- **The build-time gate.** Extract every resolved capability identifier from the composed
  `@CapabilityModule` graph and assert `Capabilities_declared ⊆ Capabilities_entitled` whenever the
  build targets production (`-Pproduction`). A missing entitlement fails the build with a
  diagnostic that names it.
- **No phone-home.** The check is local: nothing in the tooling pipeline opens a network
  connection to learn what is entitled.
- **A development build is never gated.** Without a production target the assertion does not run,
  and an unstamped artifact is a valid output.

`exeris:verify-capabilities` (`VerifyCapabilitiesMojo`) already validates the composed capability
graph against the processor's fresh output; the entitlement assertion is not implemented yet.

## When to consult ADR-089 from exeris-tooling

- Any change to capability verification: `VerifyCapabilitiesMojo`, the `cap-manifest.json`
  emission, or the `@CapabilityModule` validation in the processor.
- Adding a production-target profile, or anything that stamps an artifact for production.
