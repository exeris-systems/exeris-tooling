# 0.12.0 release plan

0.12.0 has no date; its scope closes it. **Put the annotation-coverage guard in place and emit the
attributes that need no new SDK half; close the open defects; build a static site from `@View`
metadata without hand-written routes, shell or 404; and let a generated service publish its
contract, consume a peer's, and receive a peer's events.** The
[ROADMAP](../ROADMAP.md) "0.12.0" section keeps the checklist and points here. This note holds the
order, the gate on each item and the Java/TS pairing.

**Pins.** SDK 0.13.3 and kernel 0.13.2, both final on Maven Central. Kernel 0.13.2 changes no SPI
type and no main source of `exeris-kernel-spi` or `exeris-kernel-core`; it adds client
configuration, a manual-commit mode and a raw record channel to the Community Kafka binding, and
its BOM manages Jackson 3.3.0 and the PostgreSQL driver 42.7.14. 0.12.0 does not wait for an SDK
release: a row that needs a carrier or an `-io` reader half SDK 0.13.3 lacks is in 0.13.0
([annotation coverage plan](1.0.0-annotation-coverage-plan.md)). A row needing an SDK 0.13.x patch
enters only if the patch is final on Central before the cut. No cross-repo SNAPSHOT at the cut
(Versioning policy).

**Where this applies.** The rows below are the whole of 0.12.0. The coverage rows are the subset of
the annotation coverage plan's 0.12.0 and wave 0 lists that SDK 0.13.3 already carries; that plan
stays the authority for the disposition of every annotation and attribute.

**The trade-off.** Cutting on SDK 0.13.3 keeps the release off another repository's calendar and
moves seventeen coverage rows to 0.13.0, which becomes the release that pairs with the next SDK.
The service rows ship a contract, a client and an event subscriber, and no replicated table: on the
Kafka binding the kernel runs no transactional outbox, so an entity write and its publish are two
writes until the kernel composes them, after its 1.0.

**Gate vocabulary:** as in the 0.11.0 plan — **none**, **RFC/ADR** (number reserved in
`exeris-docs/adr-index.md` and on `main` before the content), **upstream** (a kernel or SDK issue;
the row enters only if that half is final before the cut). An accepted ADR is amended with a dated
section, never edited.

## Wave 0 — decisions

- [x] **W1 — disposition registry format (#535).** [ADR-110](adr/ADR-110-every-sdk-annotation-and-attribute-carries-one-disposition-held-to-the-sdk-catalogue.md): the registry's row shape and states, the
      catalogue it is checked against, and how `INERT_ATTRIBUTES`, `INERT_ANNOTATIONS` and
      `UNREAD_NOTES` relate to it. Feeds G1.
- [x] **W2 — view emitter shape (#543).** RFC-2026-06-28 accepted, then the emitter-shape ADR it calls for, [ADR-111](adr/ADR-111-view-emitter-shape-owned-routes-and-site-shell-typed-built-in-blocks-convention-resolved-custom-blocks.md):
      typed props for the built-in blocks, the site shell from `@View.layout`, a `SECTION` view as a
      part of the shell, and which files of the emitted app the generator owns on every run. Feeds
      V2 to V6.
- [x] **W3 — `customBlocks` source of truth (#417).** Decided in the W2 ADR, [ADR-111](adr/ADR-111-view-emitter-shape-owned-routes-and-site-shell-typed-built-in-blocks-convention-resolved-custom-blocks.md): a reference in the
      view IR, a naming convention with an override, or a registry file in the app. Feeds V7.
- [x] **W4 — contract of a backend without `@CapabilityModule` (#391).** [ADR-048 Amendment 3](adr/ADR-048-cross-app-contract-mesh.md#amendment-3--every-backend-publishes-its-contract-and-the-registry-slices-manifest-shape-2026-11-28): what
      such a backend publishes, the artifact inside the jar, resolution by Maven coordinate beside
      a directory path, and the manifest shape of the registry slice within `schemaVersion` 2.
      Feeds M1 and M2.
- [ ] **W5 — service workspace and run (#551, #423).** An ADR-091 amendment: a workspace of several
      services, adding a service to an existing workspace, the compose file, a run goal or a
      launchable jar, and migrations at start. Whether migrations at start belong to the kernel or
      to this repository is decided here. Feeds M4 to M6.
- [ ] **W6 — events across services (#553).** RFC, then ADR. The event specification a contract carries,
      the generated subscriber for a peer's events, delivery semantics, tenant isolation across
      services, and what is deferred. Feeds R1 to R3. It records as constraints, measured on kernel
      `v0.13.2`:
      - the Kafka binding runs no transactional outbox (kernel ADR-101 Ruling 3);
      - consumption is at-most-once unless the consumer commits manually, there is no dead-letter
        topic, and deduplication on the event id is the application's;
      - a consumer subscribes only to event types in its own registry, so a consuming service
        registers the publisher's `EventTypeSpec`; whether delivery routes by ordinal or by name is
        established in the RFC;
      - emitted code names no broker: the generator stays on the `EventEngine` SPI, and a broker
        appears only in what the initializr writes.
- [ ] **W7 — event envelope (#555, #524).** A new ADR: the fields every published payload carries beside
      the declared ones (coverage row JA12). Feeds B2 and R1.
- [ ] **W8 — API surface switches (#539).** A new ADR for `@ExerisDomain.restApi` and `internalClient`
      (coverage row J14). Feeds J14 and S7.
- [ ] **W9 — `@Saga.trigger` (#538).** A new ADR (coverage decision W0-6): `EVENT`, `API` and `MANUAL`
      triggers, `SCHEDULED` refused, and the destination of each compensation attribute. Feeds J6.
- [ ] **W10 — rules recorded in their pull requests:** an absent `inCreate` or `inUpdate` key
      (#401); the refusals for a standalone `@Saga` (#489); the two-pass build (#424); a `@Requires`
      on a kernel SPI type (#409, an amendment to the capability ADR); an index on a `List` column
      (#517). Where a rule changes an accepted ADR, the pull request carries the amendment.
- [ ] **W11 — stretch, due before the SDK 1.0.0-RC:** the ADRs of the rows now in 0.13.0 —
      `@InternalApi` (W0-3), `@Action.path` and `httpMethod` (W0-4), soft-delete restore (W0-8),
      `@PrimaryKey.allowClientId` (W0-10), and the event publisher.

## Not in 0.12.0

- **Coverage rows that wait on an SDK half:** JA2 to JA5, JA10, JA11, JA13, JA15 and SA1 to SA4,
  SA8 of the annotation coverage plan's 0.13.0, and the emission of the event envelope (JA12, SA6).
- **`@Channel`** (JA9, SA5; #438): no `-io` reader half in SDK 0.13.3, and the kernel's WebSocket
  SPI is preview.
- **A replicated table of a peer's entity**, `@Projection` and `@EventHandler`: after W6 and the
  behavioural corpus (coverage decision W0-11, #425).
- **Entity pages in a prerendered site** (a list and a detail page per row) and **build-time data**:
  they need a data source in the view IR. The **`FORM` block** and **message keys** (`titleKey`)
  follow the TS rows that carry the translation hook.
- **#443, #445:** they go with the SDK 1.0 pin.

## The cut

**Criterion:** A0, A1, G1, G2, J1, J2, J6, J14, S2, S4, S7, B1 to B10, V1 to V8, V10, M1 to M6,
R1 to R3, T1, T2, H1 and H2 are closed, or each open item has moved to a named milestone with its
ROADMAP entry. The G1 test passes against the SDK 0.13.3 catalogue, and each `OPEN` row names its
row in the annotation coverage plan. `contract-coverage.ts` reports 0 GAP and the TCK binding's
`unsupportedFacets()` is empty. The prerendered sample app builds the cases of V1 to V8. R3 passes
on the commit that is tagged. No issue labelled `bug` is open in the 0.12.0 milestone. V9 enters
only on a final SDK patch. A row whose wave 0 decision is not accepted when its implementation
would start moves whole to 0.13.0.

**Sequence:** as in the 0.11.0 plan: final pins, the release PR (which assembles
`docs/migration/0.12.0/` with `tools/migration/assemble-migration.py --release 0.12.0`), a dry run
of `release.yml` from `main`, the tag, Central, npm, then `0.13.0-SNAPSHOT`.
