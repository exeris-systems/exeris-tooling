# 0.10.0 release plan

0.10.0 has no date; its scope closes it. **Compile route authorization (T53), make a streaming
action run and stream its events with a tenant guard (EV1-stream + T59), and remove what 0.9.0
deprecated.** The cross-app mesh (T12 + T17) is the stretch wave: it goes last and does not hold the
cut. The [ROADMAP](../ROADMAP.md) "0.10.0" section keeps the checklist and points here. This note
holds the order, the gate on each item and the Java/TS pairing. Per-item evidence lives in the pull
requests that close them, as in [`codegen-ts-track-plan.md`](codegen-ts-track-plan.md).

**Pins.** 0.10.0 pairs with kernel 0.13, and with SDK 0.13 if one is needed, provided each is final
on Maven Central before the cut. Otherwise it cuts on the `0.12.0` pins it has. Either way, no cross-repo SNAPSHOT at the cut
(Versioning policy).

**Already in the train.** The reactor, `exeris-app-bom` and `@exeris/codegen-ts` are at
`0.10.0-SNAPSHOT` (#307). From 0.10.0 every module is published under the `eu.exeris` group (#308; ADR-091
Amendment 4, ADR-095 Amendment 1, MIGRATION "0.10.0 train").

## How to read the waves

The Java and TS tracks run as separate wave sequences. A TS wave that consumes a Java contract
starts after the Java wave that defines it, and the pairing is stated on the row. Within a track, a
wave with no gate can run as soon as the previous PR merges. PRs are sequential, because each one
moves `main` and the next one rebases onto it.

**Gate vocabulary:**

- **none** — this repository alone.
- **RFC/ADR** — a decision document first. Reserve its number in `exeris-docs/adr-index.md`, and get
  the row on `main` before the ADR's content.
- **upstream** — a kernel or SDK issue. The item is *conditional*: it enters 0.10.0 only if the
  upstream half is final before the cut.

J0 does not hold the cut: it hardens the build and changes no emitted output. The Java-lint baseline
it starts from, warn-only on JDK 26, is 217 Checkstyle and 19 PMD violations; the commits that wire
the plugins and narrow the import ban give them per module and rule.

**J2b — the bridge contracts.** `exeris-ai-bridge` needs the catalogue to name the generator of a
generated file (`build-explain_artefacts`) and the jar to run the Java generator
(`build-preview_generation`). J2b does not hold the cut. It runs after J1 and before J3 and J4: once
the conformance test is on `main`, every later PR that adds or moves an emitted file adds its
catalogue row in the same PR.

**T53 — the RFC must settle** (ROADMAP T53 entry):

- how a path template matches the concrete path the dispatcher passes;
- what an undeclared route gets: `PERMIT_ALL`, or `unmatched()`'s `AUTHENTICATED`, which would lock
  every existing app;
- ANY_SCOPE or ALL_SCOPES for an entity's `permissions`;
- how an `@Action`'s permissions compose with its entity's;
- where the policy binds, given that `HTTP_ROUTE_POLICY` is a `ScopedValue` around boot that
  `RuntimeComponents` cannot reach;
- what the FE guards read once names are declared.

It also takes C2's `readRoles` / `writeRoles` / `bypassRoles`. Read kernel 0.12's
`RouteRequirement.Execution{PROMPT, LONG_RUNNING}`, `abstain()` and `HttpRoutePolicy.firstDeclared`
first. Only `permissions` has a destination; `roles` belongs to the kernel's `@RequiresRole`.

**ADR-044 Amendment 2 — the questions**, from the ROADMAP EV1-stream entry plus the two this plan
adds:

1. When an invoke-then-stream response closes after the action has run.
2. The in-stream error frame when the action fails after the head is written.
3. Frame names: `streamEventType` against the `@DomainEvent` names the action triggers.
4. Frames from concurrent invocations on one aggregate interleave, because `EventDescriptor` carries
   no correlation id.
5. Obligation 4 forbids heap-queue buffering, while the shipped entity-level producer uses a bounded
   drop-on-full queue. Admit it, or avoid one in the per-action driver.
6. Tenant isolation (T59).
7. *(added)* A GET route for `EventSource` consumers.
8. *(added)* The emitted `EventBusService` default endpoint `/api/v1/events/stream`
   (`event-gen.ts`), which no server route serves: fan-in, a consumer-supplied endpoint, or none.

## The cut

**Criterion:** J1–J5 and S1–S4 are closed, or each open item has moved to a named milestone with its
ROADMAP entry. Stretch and conditional rows do not hold the cut, nor does J2b, nor does any part of a
row whose gate is upstream (the T59 isolation key and the tenant stream clients that wait on it).

**J3 holds the cut, with one exception.** If exeris-sdk#161, the `-io` reader half, is not in a final SDK
release before the cut, the processor does not write `routeAccess` (ADR-042: a released pair must not
disagree). In that case J3 ships the route policy only for what the reader already carries, or moves
whole to 0.11.0 with the 0.9.0 refusal in place. The ADR states which.

**What this rule costs.** 0.10.0 can ship with streams still refused on tenant-partitioned entities.
That leaves the live views a multi-tenant app most needs, Stellar's included, on the 0.9.0 refusal.
It can also ship without the mesh and without the saga work Track C and `@SagaTransition` carry. Each
slip costs a train of waiting, not a release of broken output: the item stays refused or unemitted,
as in 0.9.0.

**Sequence:**

1. Final pins (kernel `0.13.0` if final, SDK `0.13.0` if needed and final; otherwise `0.12.0`).
2. Release PR at `0.10.0`: reactor, `exeris-app-bom`, `@exeris/codegen-ts`, and the README quick start
   on `eu.exeris` and `0.10.0`. The same PR runs
   `python3 tools/migration/assemble-migration.py --release 0.10.0`, which inlines
   `docs/migration/0.10.0/` into MIGRATION's 0.10.0 train and deletes the fragments; the readiness
   gate fails a release that skipped it.
3. Tag.
4. Deploy to Central, then Publish in the Central Portal.
5. Stage `@exeris/codegen-ts` on npm, then approve with 2FA.
6. `0.11.0-SNAPSHOT`, with MIGRATION's `0.11.0 train` heading and its empty marker block
   ([migration fragments](migration/README.md#the-cut)).
